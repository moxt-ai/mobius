Long session, no raw-history archive

Flow while active.
Reclaim at completion.

Only the active turn keeps raw event payloads in the Session DO. Text deltas are packed in active stream blocks; its terminal transaction persists a canonical message, retains a payload-free idempotency receipt, then deletes that turn's raw payloads and blocks. A refresh restores stable history from /messages, never by replaying old deltas.

Core boundary
Completed raw events are not archived to R2.

Raw events serve the current stream, brief reconnection, and commit idempotency; once complete, their UI meaning is absorbed by the canonical message read model. When R2 is used, it stores only tool-detail artifacts that a read model cannot reconstruct.

Key distinction: completion is still delivered to a currently connected realtime subscriber. Only a client reconnecting later with an expired cursor cannot demand raw replay; it obtains the same complete conversation state through /messages.

Why an active turn has no rolling hot tail

A generating turn needs all of its still-unfinalized raw events for realtime delivery and reconnect compensation. Splitting it mid-turn would fork its recovery semantics, so it stays wholly in the DO until its terminal transaction reclaims it.

Why the receipt has no payload

If an ACK is lost, the daemon can resend a terminal event. The receipt only needs to prove that the same event ID, hash, and source sequence committed, so it can return the original cursor idempotently; it need not retain displayable JSON.

Why history still recovers in full

At the terminal boundary, all active stream blocks are folded into session_messages in the same transaction that reclaims raw data. Deleting raw events therefore leaves /messages able to return the complete, stable conversation.

When is a raw event actually needed?

It is short-lived protocol material, not a second permanent history for a completed session.

Realtime output

While the browser subscribes, delta boundaries and payloads are required for incremental rendering.

Active-turn continuation

After a brief disconnect, an unfinalized turn can use the latest message cursor to fill in exact events.

Terminal-event idempotency

After raw deletion, the payload-free receipt still identifies a resend of the same terminal event caused by a lost ACK.

Capacity boundaries

what the limits now mean

  • activeRaw events are not cut into a historical hot tail; all raw events for an unfinalized turn stay in the DO until its terminal transaction completes.
  • 256 KiBThe target packing size for an active delta stream block; it bounds rewrite cost without splitting one event.
  • 1.5 MiBThe UTF-8-safe DO row budget for canonical-message continuation and active activity-detail content chunks.
  • 128 KiBThe uncompressed physical-segment limit before an R2 write still applies when archiving a large activity detail.
  • 192 KiBThe capacity guard for one compressed artifact segment. It does not constrain raw events because raw never travels through R2.

04 / DECISIONS

Three intentional tradeoffs in this design

It separates a fast realtime protocol from stable historical reading instead of making R2 a permanent raw-event extension.

Keep a generating turn fully hot

A long turn can temporarily consume DO raw-event space in exchange for simple, continuous realtime and reconnect semantics. Completion reclaims it, so growth never accumulates as hot history for the whole session.

Delete raw at termination; do not move it

Projection already persists final text, tool summary, and state. Creating an R2 range archive for an input copy no historical UI uses only adds writes, indexes, recovery work, and failure surface.

An expired cursor is an explicit contract

Historical raw deletion is not silent loss: an event request before the minimum sequence gets cursor_expired, so the client knows to recover from a /messages snapshot.

For an active turn that exceeds the former hot window, every delta remains in a DO stream block and is continuously readable through /events.

Terminal path

Canonical-message materialization, minimum-cursor advancement, event-and-block deletion, and a payload-free receipt occur in one DO transaction; a terminal resend remains idempotent.

Recovery path

A page restores the full reply with /messages alone; it loses no text and does not rejoin deltas because raw data has been reclaimed.

06 / GUARDRAIL

“No raw history” does not mean “no conversation history”.

Raw payload and message history are different material. The former serves current transport; the latter serves a user's stable, visible conversation.

!

The factual source for a completed turn is its turn read model, not an R2 raw replay.

If a future feature needs a full protocol audit, replayable trace, or model-debug data, make it an explicit, separate audit product with its own retention policy. Do not quietly depend on a raw-event archive for ordinary chat-history recovery.
